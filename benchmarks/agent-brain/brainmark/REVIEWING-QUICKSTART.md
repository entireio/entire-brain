# REVIEWING-QUICKSTART — the seal session, one page

Two raters. Read `SEAL_PROTOCOL.md` §"Accept / reject criteria" once before you
start (5 minutes); that is the calibration. **Do not discuss any pair with the
other rater, or look at their verdict, before you have recorded your own** — the
kappa is only inter-rater reliability if it is measured before anchoring.

## What is in front of you

`review/` was generated by `seal_prescreen.py` from 1,806 mined candidates:

| file | what it is |
|---|---|
| `review/sheets/INDEX.md` | the checklist — 350 pairs in rank order. `D` = proposed dev split, `!` = miner flagged it, judge `LEAK` individually |
| `review/sheets/NNN_<pair>.md` | one sheet per pair: both problem statements, both gold patches, the shared files, the miner's scores, the criteria table |
| `review/REVIEW-rater_1.json`, `review/REVIEW-rater_2.json` | **your** file. Fill in your own row only |
| `review/SLATE.json` | why each of the 1,806 candidates is or is not on the slate |
| `review/patches/`, `review/statements/` | the untruncated bytes a sheet links to |

The slate is 350 because 1,806 is unreadable and 40 is what the pre-registration
needs (30 sealed + 10 dev). Its order is fixed **before** any verdict exists —
that is the whole point of `SLATE.json` — so working it in order is not cherry
picking. Deviating from the order after seeing verdicts is.

## Time

2–3 minutes a pair. The full slate is 12–17 hours each; you do not need the full
slate. The plan below is ~80–110 pairs, i.e. **3.5–5.5 hours each**:

1. **The 20 `D` pairs first** (~50 min). The dev split must be drawn before the
   sealed split, so a pair that was debugged against can never quietly end up in
   the confirmatory set. From the ones you both accept, assign exactly 10
   `"split": "dev"` — take them in rank order, no discretion.
2. **Then rank order from 001**, skipping `D` pairs, `"split": "sealed"`, until
   30 are accepted by both of you. At a 40–50% accept rate that is 60–90 pairs.
3. Everything past that is reserve. Stop; do not keep reading to improve a number.

**Fix the stopping rule before the first verdict** and write it down. Taking the
highest-ranked accepted pairs means the sealed set is the pairs with the
strongest file/symbol overlap — defensible (that is where A→B dependence is most
likely) but a selection, and it goes in `DATASHEET.md`. If you would rather seal
a representative sample, pre-commit to a block (e.g. every 4th slate entry) now,
not later.

## Filling it in

In **your** `review/REVIEW-<you>.json`, for every pair you judge:

```json
"pairs": {
  "<pair_id>": {
    "reviews": {
      "rater_1": { "verdict": "accept", "criteria": ["DEP"], "notes": "why" }
    },
    "split": "sealed"
  }
}
```

- `verdict` is exactly `"accept"` or `"reject"`. Blank is not "reject" — it
  refuses the whole promotion.
- **A reject MUST cite ≥1 code** from `DEP` / `LEAK` / `TRIV` / `REVEAL`. An
  accept may cite codes too (e.g. `DEP` to record why it is strong).
- `split` only on pairs you accept. Leave the other rater's row alone.
- Record a verdict for every pair you *reach*, including rejects. Pairs neither
  of you reached are dropped at merge time and listed; a pair one of you skipped
  refuses the promotion, which is deliberate.

## After both files are done

```bash
python3 brainmark/seal_prescreen.py --merge-reviews \
    brainmark/review/REVIEW-rater_1.json brainmark/review/REVIEW-rater_2.json
#   -> brainmark/REVIEW.json  + a count of dually-reviewed / dropped pairs
python3 brainmark/seal.py promote      # kappa + sealed/ + dev/ + SEAL-MANIFEST.json
python3 brainmark/seal.py verify
```

**Adjudication.** Where your verdicts differ, the pair goes to a named
adjudicator — fill `adjudication.resolved_verdict` and
`adjudication.adjudicator` in the merged `REVIEW.json`. Do not quietly change a
verdict to match the other rater: that destroys the disagreement, which is the
record. A pair you both reject, or both accept, is not adjudicated.

**Cohen's kappa** is computed across every dually-reviewed pair (rejects
included) and written to `SEAL-MANIFEST.json.seal_v2`. It is **reported whatever
it is.** Below ~0.61 the honest response is to revisit the criteria wording in
`SEAL_PROTOCOL.md` and re-review a fresh sample — never to override the
lower-scoring rater or re-seal until the number improves.

**`promote` refuses** — before writing anything — on: a rater with no
name/affiliation, a pair missing either verdict, a reject with no criteria code,
an unadjudicated disagreement, fewer than 2 dually-reviewed pairs, sealed/dev
overlap, or counts short of `config.json` (`--allow-short` only for a declared
pilot, recorded in `PREREGISTRATION.md`).

## The dev-split rule

`tasks/dev/` (10) and `tasks/sealed/` (30+) are **disjoint**, and dev is drawn
first. Dev is burned freely: harness debugging, the null test, the pilot. Sealed
is touched **once**, at the end. A dev pair is never promoted into sealed later —
that would launder a debugged pair into the confirmatory set. Both splits are
hashed into the one `SEAL-MANIFEST.json`; `report.py` recomputes every hash and
prints `REFUSED` rather than aggregating if any byte moved.
