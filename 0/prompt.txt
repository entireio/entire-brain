<result>Not clean. Arming in `cli.Execute` is the right layer, but the detached exemption is too narrow: it lives in one spawn helper when it should follow what "detached" means.

**1. The marker covers one detach path, but the codebase has two.** (`internal/cli/setup_spawn.go:37-44` and `internal/cli/memory_cmd.go:129`)
- `launchDetachedSelf` is a second detach primitive. It is used by `memory notify` (`memory_cmd.go:124` and `memory_notify_sync.go:30`) to start a `memory worker --once` that is meant to outlive the short-lived notify process. Its own comment says "if this process exits first, the child is reparented and keeps running".
- It doesn't go through `spawnDetached`, so it never gets `ENTIRE_BRAIN_DETACHED=1`. With `cli.Execute` now arming the watchdog for every process, that worker is exposed to it.
- The marker is also an inherited environment variable. Any `entire-brain` process started from inside a detached child, such as a backfill re-exec, inherits it and skips the watchdog. That is the same orphan risk one level down.
- In short, the exemption is tied to "called through `spawnDetached`" rather than to "this process was deliberately detached".

**2. Session leadership is the deeper mechanism, and the code already relies on it.** (`internal/cli/internal/parentwatch/parentwatch.go:20` and `internal/cli/setup_spawn_unix.go:12`)
- On Unix, `spawnDetached` already makes the child a session leader with `Setsid: true`. launchd and systemd jobs are also session leaders.
- A check like `unix.Getsid(0) == os.Getpid()` in `shouldArm` would cover both current exemptions (initial ppid 1 and the marker) with one fact the OS reports. Unlike an environment variable, it doesn't pass down to grandchildren.
- `launchDetachedSelf` should then use `detachedSysProcAttr()` too, so both detach paths share one definition of "detached" and both are exempt.
- The environment marker would only be needed on Windows, where `CREATE_NEW_PROCESS_GROUP` can't be checked from inside the child.

**3. Arming in `cli.Execute` and handling this at the process level are both right.** (`internal/cli/root.go:50` and `internal/cli/internal/brainstore/filelock.go:45,172`)
- Whether `entire` dispatched this process is a property of the process, not of a command. Arming per command would repeat the call in every verb that takes the lock.
- The lock layer has nothing that would solve this more generally. `BrainWriteLockTimeout` (10s) only limits how long other processes wait for the lock, not how long the holder keeps it. There is no lease, and the kernel already releases `flock`/`LockFileEx` when the holder dies.
- So ending the orphaned process is the correct fix, not a duplicate of an existing mechanism.</result>
