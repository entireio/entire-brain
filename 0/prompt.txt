<result>The per-run file reads are not where the cost is. Both files are tiny, and reading them costs microseconds, far less than starting the plugin process. The real problems are on the path that runs once a day, and three of them can stall or repeat the `git ls-remote`. Ranked by impact:

**1. The 2s timeout does not actually cap the stall** (`cmd/entire/cli/plugin_versioncheck.go:76`, through `cmd/entire/cli/plugin_gitremote.go:119-137`)
- **Summary:** When the 2s deadline hits, Go kills only the `git` process. `runGitQuiet` sends stdout and stderr to custom writers (`limitedWriter`), so Go copies them through pipes, and it sets no `cmd.WaitDelay`. Git's child processes (`git-remote-https`, or `ssh` for ssh remotes) inherit the stderr pipe. `cmd.Run()` waits for those pipes to close, which only happens when the orphaned children exit on their own network timeouts. So the "at most 2s" pause after a plugin run can last much longer. That bug already existed for interactive installs, but this change puts it on a path that hooks and agents hit constantly.
- **Cheaper alternative:** set `cmd.WaitDelay` (for example 100–250ms) in `runGitQuiet`, or put git in its own process group and kill the whole group when the deadline hits.

**2. A failed cache save means `git ls-remote` runs on every invocation** (`plugin_versioncheck.go:75-85`, `:136`)
- **Summary:** The network call happens first, and only then is the cache stamped. If the config directory can't be written (sandboxed agents, read-only `$HOME`, containers), `savePluginVersionCache` fails, the failure is only logged at debug level, and every later `entire brain`/`graph` run pays the full ls-remote again. The CLI's own `versioncheck.CheckAndNotify` avoids this by returning early when `ensureGlobalConfigDir` fails, before it touches the network.
- **Cheaper alternative:** open `userdirs.ConfigRoot()` (or write the stamp) before the network call, and return without the ls-remote if that fails.

**3. Parallel runs all fire `git ls-remote` at once** (`plugin_versioncheck.go:70-82`)
- **Summary:** The stamp is written only after the ls-remote finishes, up to 2s or more later. Agents often run several `entire brain`/`graph` calls in parallel or in quick succession from hooks. Every run that starts while the stale check is in flight passes the gate and starts its own ls-remote.
- **Cheaper alternative:** write `LastCheckTime = now` right after the gate passes and before the network call. It's a cheap claim: there is a small race window, but no N-way fan-out.

**4. The two post-run checks run one after the other** (`cmd/entire/cli/plugin.go:180-182`)
- **Summary:** `postPluginVersionCheck` (2s HTTP budget) and then `postPluginUpdateCheck` (2s git budget, more given finding 1) run in sequence. On a run where both are stale, such as the first run of the day, the user waits up to about 4s+ after the plugin has already exited.
- **Cheaper alternative:** run both checks in goroutines that each write to a buffer, wait for both, then print the buffers in a fixed order. The worst case becomes max(a, b) instead of a + b. Notices still never interleave.

**5. Minor: the manifest is read and parsed before the cheaper 24h gate** (`plugin_versioncheck.go:62` vs `:70-71`)
- **Summary:** On almost every run the 24h gate is what returns early. The current order still opens the plugin root, reads `manifest.yml` and runs a reflection-based YAML parse before reading the JSON cache. The cost is tiny (tens of microseconds), so this is tidiness, not a real hot-path cost.
- **Cheaper alternative:** load the cache and check `time.Since(...)` first, then call `LoadPluginManifest` only once the cache is stale. The two reads aren't otherwise linked; the pinned and no-manifest checks still work after the reorder.

- Both directory handles come from the shared cached handle (`osroot.Shared`), so nothing is reopened per call.
- The cache file is one JSON map that grows by one small entry per installed plugin. Pruning it isn't worth doing.
- There are no long-lived closures; the deferred cleanup closure in `savePluginVersionCache` is short and holds only `root` and `tmpName`.
