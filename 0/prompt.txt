<result>## Verdict

Mostly right altitude for the *idea* (one long-lived `cat-file --batch` child per repo is the correct fix for N-execs), but the *wiring* is one layer too shallow: it is bolted on at two call sites via a concrete-type check and re-derives the git spawn policy by hand, next to a file that explicitly documents "one spawn point" as a security invariant.

## Findings

**1. `/Users/evisdrenova/conductor/workspaces/entire-brain/hamburg/internal/cli/git_catfile_batch.go:65` — `commandRunnerIsExec` asserts on a concrete type where the codebase already has a capability-interface idiom for exactly this.**
`runner.go:26` (`EnvironmentCommandRunner`) and `runner.go:36` (`CommandStreamer`) model optional runner capabilities with a buffered fallback — `CommandStreamer`'s doc comment is almost word-for-word this feature's contract. `case ExecRunner, *ExecRunner` instead means any decorator (tracing, metrics, a future remote/sandboxed runner) silently loses batching forever, and no test can exercise the batched path through the seam. Deeper change: declare `CommandObjectReader` (e.g. `ReadObject(ctx, dir, spec string, env map[string]string) ([]byte, string, error)`) in `runner.go`, implement it on `ExecRunner`, and have call sites assert the behavior, not the type.

**2. `git_catfile_batch.go:94` — this is now the second place in the binary that spawns `git`, re-deriving the hardening preamble by hand.**
`git_harden.go:189-194` states the invariant verbatim: hardening "is applied at the single point where this binary actually spawns git (see runner.go), which is what keeps it unbypassable: every call site in every package ... is covered without each one having to remember." The new child re-does `hardenedGitArgs` + `repoFilterDriverOverrides` + `mergeCommandEnv` + `gitConfigOverrideEnv` itself (and omits `commandWaitDelay`). It is a faithful copy today; the next change to the preamble will cover one path only. Deeper change: factor the preamble into one `startHardenedGit(ctx, dir, env, args...) (*exec.Cmd, error)` in `runner.go` and have both `runExecCommand`/`Stream` and the batch child use it — `ExecRunner.Stream` (runner.go:148-164) already carries a third copy of the same block, so this is a pre-existing duplication the batch file makes a trend.

**3. `git_catfile_batch.go:88` — the local-only (no-egress) policy is re-encoded inline instead of flowing through its chokepoint.**
`runCheckpointGitLocal` (`export.go:685-698`) is the whole definition of local-only reads: refuse network-capable subcommands **and** fail closed when the runner cannot enforce `GIT_NO_LAZY_FETCH=1`. The batch path reproduces only the env bit, so "local-only" now has two independent definitions, one of which can't fail closed because it bypasses the runner entirely. Deeper change: have the policy be a value (`localGitEnv()` / a `gitReadPolicy` struct) produced in one place and consumed by both the per-exec chokepoint and the batch child, so adding a future bit (`GIT_TERMINAL_PROMPT=0`, a new refusal) can't cover one path only.

**4. `internal/cli/entities_cmd.go:821`, `internal/cli/verify_cmd.go:511`, `internal/entityindex/build.go:453` — the remaining per-object exec loops are not routed through the new reader.**
`partitionPresentCommits` is a literal `for _, sha := range commits { runner.Run(..., "cat-file", "-e", ...) }` — the exact shape COR-2182 describes; `verifyCommitUncached` does one `cat-file -e` exec per commit (memoized, but still per commit) and is already policy-aware; `isGraftedBoundary` does one `cat-file commit` per commit during the walk and **cannot** use the reader at all because it lives in `internal/entityindex` and the helper is unexported in `internal/cli`. Deeper change: once the reader is a runner capability (finding 1) these become `exists(spec)` / `readObject(spec)` calls against `--batch-check`, and the cross-package site stops being unreachable.

**5. `internal/cli/export.go:2812` + `git_catfile_batch.go:222` — the "batch first, `missing` is definitive, everything else falls back" rule is restated per call site.**
Both sites repeat the same three-line predicate plus its own explanatory comment; a third caller must re-remember that retrying `errCatFileBatchMissing` on the per-exec path is wrong. Deeper change: one pair of helpers (`readGitObject` / `gitObjectType`) that owns batch-attempt + fallback + policy selection, with `catFileWithPolicy` and `validateLocalTranscriptSessions` reduced to plain calls — which also makes the per-exec branch of `catFileWithPolicy` collapse into the existing `runCheckpointGitWithPolicy` (`export.go:2061`) rather than re-writing its `if localOnly` fork.

## On the header parsing (question 3)

The hand-rolled `&lt;oid&gt; &lt;type&gt; &lt;size&gt;\n&lt;body&gt;\nLF` framing itself is at the right altitude — there is no `internal/git` plumbing package, and inline plumbing parsing has precedent (`semantic_coverage.go:174` parses `ls-tree -z` in place).
