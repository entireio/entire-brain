**#4 — backwards compatibility.** The CHANGELOG since `v0.1.0` already names the breaks; the question is what policy each one gets. What shipped on main since the last stable tag:

1. **`facts` → `memories` command rename** — the biggest one. Precedent exists (`search`/`vsearch` live on as compatibility aliases for `query`), but whether `facts` got the same alias treatment needs verification, not assumption.
2. **`init-agents` removed** (folded into `setup`) — anyone's scripts or muscle memory calling it should get a clear "use `setup`" error, not an unknown-command.
3. **Code inspection now reads Graph's shared committed-tree store** — creates a real version-coupling: brain 0.2 with an old graph store, or old brain with a new store. There's a handled `errGraphStoreUnsupported` path, but the upgrade-ordering story (which binary do you upgrade first?) is undefined.
4. **Bundles format changed** (carry runtime observations, no code indexes) — old bundle into new binary and vice versa.

Plus the one nobody's CHANGELOG captures: **`.entire/agent-guide.md` is committed into users' repos.** Every repo that ran setup under 0.1.0 has a guide referencing the old command surface (`facts`, `init-agents`…). New binaries must tolerate stale committed guides, and there needs to be a re-render story (presumably "re-run setup") stated in the release notes.

There is migration machinery in the code (`loadMemoryMigrationProgress` in memory_admin.go) but I haven't verified it covers the full store — that's audit work, not discussion work.

The deliverable I'd scope: a **compat policy + evidence matrix**, roughly:

| Scenario | Required behavior |
|---|---|
| 0.1.0 store opened by 0.2.0 | auto-migrate forward, or `refresh` with a clear prompt |
| 0.2.0 store opened by 0.1.0 (downgrade) | refuse cleanly, never corrupt |
| brain 0.2 + old graph / old brain + graph 0.5 | work or fail with a named version requirement |
| Removed/renamed commands (`facts`, `init-agents`, `search`) | alias for ≥1 minor, or error naming the replacement |
| Stale committed agent-guide | tolerated; setup re-run refreshes it |
| JSON `schema_version` fields | unchanged or bumped additively |
| MCP `brain_*` schemas | byte-diff vs 0.1.0: unchanged or additive |
| Hosted wire | old client vs current server (the ≥-version gate precedent) |

The one policy question that decides how strict this matrix is: for 0.2.0, is your promise **"no silent breakage"** (everything either works, aliases, or fails with a message naming the fix — my recommendation, cheap and honest) or the stronger **"0.1.0 workflows keep working unchanged"** (every rename needs a working alias, which means re-adding whatever's missing)?
