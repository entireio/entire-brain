I pushed this into a local branch: model-adaptive-brain.

The main change is that I moved the adaptation into the benchmark/context protocol rather than the core brain engine. Validation commands and scoring are unchanged.

The original approach. more brain context, helped some models but hurt others by causing extra searching and token usage. The new version is model-adaptive: compact packets + stop rules for stronger models, checklist-style packets for smaller models.

Results

• GPT-5.5

Original: 94 → 95, slower, +57% tokens
Change: compact packet, no forced brain brief
New: 83 → 95, 157s → 90s, 515k → 318k tokens

• GPT-5.4-mini

Original: 92 → 95
Change: standard checklist packet
New: still brain-positive

• Claude Opus

Original: 96 → 91
Change: compact XML packet + stop/validation rules
New: 88 → 93, 89s → 79s, 567k → 492k tokens

• Claude Sonnet

New: 93 → 93, 118s → 49s, 1.37M → 659k tokens

• Claude Haiku

  Verdict: the detector is a solid, safe, well-tested artifact — but it is NOT ready to
  be presented as proven, because the A/B that justifies it is circular and the "0

  ✅ What's genuinely solid (verified)

  - Engine design is sound and narrow: two high-precision shapes
  (operand-survives/id-swapped changed; assignment-absent-everywhere deleted, opt-in).
  Real precision guards: comment-skip, test-skip, global-presence check,
  locus-prioritized ordering, confidence scoring.
  - Read-only & safe: no writes; RE2 regexes (no ReDoS); path-traversal guard is sound
  — I tested it independently: a/../../etc/passwd, foo/../../../etc/passwd, absolute
  paths all blocked or contained, zero escapes.
  - Tests are real, not tautological: 4/4 pass, including a genuine clean-tree negative
  (exercises the presence guard) and the opt-in-deletion test. Determinism/UTF-8/CRLF
  handling verified safe.

  🔴 Blocking problem: the eval can't honestly demonstrate the benefit

  1. The A/B is circular (CRITICAL, verified). run.py:1580 tells the agent: "…restore 
  expected exactly in place of current," and mcp.go:261 returns
  file/line/expected/current. The harness computes the fix and the agent pastes it —
  this measures transcription, not detection. (In fairness: the arm is explicitly
  Experimental, env-gated A/B (default OFF) with honest comments — the danger is only
  if its pass-rate lift gets surfaced as a "radar win." Finding #8: nothing flags it as
  answer-assisted in the report.)
  2. "0 false alarms" is degenerate (CRITICAL, verified). regression_eval.py:62 =
  len(clean) on the same 2 tuned tasks, against a tree that still holds the invariant —
  the guard suppresses by construction. It's not a precision measurement; it can't
  return non-zero.
  3. Unproven marginal value. The detector reads expected straight from history that
  already contains the answer — so its value over a plain brain_history grep is
  currently unmeasured. Needs a brain_history-only control arm.

It's basically what entire-sem could evolve into, not what entire-brain is today. Entire-brain is still a static code graph with no memory or provenance layer.

The pieces they have that we don't are:

Real hybrid search (BM25 + local embeddings)
Directed call-flow tracing
A nice shape_check that compares response structure against how consumers actually use it

The search piece is the meaningful gap. We're still doing substring matching, while they're running embeddings locally, so they get much better retrieval quality without breaking the no-egress model.

That's probably the only thing I'd seriously consider borrowing. Local embedding search is a substantial quality improvement and fits cleanly behind the provider boundary.

I'd skip the Cypher layer, clustering, and LLM wiki features. They're either off-mission or require egress to be genuinely useful.

Where they can't really compete is the temporal side: session memory, the regression detector, and the hard no-egress guarantee. Their view of the system is purely the current code state. Ours can reason about how the system has evolved over time.
